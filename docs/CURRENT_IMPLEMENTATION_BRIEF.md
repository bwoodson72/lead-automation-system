## Status

Read `AGENTS.md` and `docs/PRODUCT_SPEC.md` first. This brief overrides the existing product spec **only where it changes messaging hierarchy, homepage copy, product-card framing, and above-the-fold product-page positioning**.

---

# 1. Why This Revision Exists

The current website explains the system, workflow, architecture, and four tiers, but it does not answer the buyer's most important question quickly enough:

> How does this make my life or business better?

The site currently risks leading with machinery before establishing the value of the machinery.

The new hierarchy must be:

```text
PROBLEM
  ↓
DESIRED RESULT
  ↓
BUYER BENEFITS
  ↓
HOW THE SYSTEM PRODUCES THOSE BENEFITS
  ↓
WHY THE METHOD IS DIFFERENT
  ↓
WHICH TIER FITS THE BUYER
  ↓
PRODUCT DETAIL / PROOF
  ↓
PURCHASE
```

Do not remove technical specificity. Reorder it so the buyer understands why the technical system matters before being asked to care about its architecture.

---

# 2. Primary Buyer Outcome

The core benefit of Lead Automation System is:

> Spend less of your working time hunting for the next web-development client and more of it doing paid work, talking to qualified prospects, or running your business.

The product does this by teaching the buyer to turn fragmented prospecting tasks into a repeatable system and progressively automate the repetitive parts.

The website must never promise that the system guarantees clients, revenue, responses, or a full pipeline.

The promise is a **better prospecting process**, not guaranteed sales results.

---

# 3. Four Benefits the Website Must Sell

Every major sales page should reinforce these four benefits before dwelling on implementation details.

## Benefit 1 — Get prospecting time back

Manual prospecting requires repeated low-value work:

```text
search
→ open websites
→ decide whether a business is worth contacting
→ find contact information
→ determine what to say
→ write the message
→ record the lead
→ remember the follow-up
→ repeat
```

The guides progressively reduce how much of this work the freelancer must initiate and perform manually.

Do not use unsupported time-savings numbers.

Use wording such as:

> Spend less time opening businesses one by one, hunting for contacts, writing every message from scratch, and rebuilding your prospect list every time work slows down.

## Benefit 2 — Make prospecting consistent instead of boom/bust

A common freelance cycle is:

```text
Need work
  ↓
Prospect heavily
  ↓
Win client work
  ↓
Get busy
  ↓
Stop prospecting
  ↓
Project ends
  ↓
Pipeline is empty
  ↓
Start over
```

The system gives the freelancer a repeatable operating process that can continue more consistently as automation increases.

Do not claim that the system guarantees a steady stream of clients.

Sell the benefit as **consistent prospecting activity and pipeline discipline**, not guaranteed pipeline results.

## Benefit 3 — Waste fewer outreach attempts on weak prospects

Evidence-first qualification is a buyer benefit, not merely a methodology.

Translate it into:

> Stop spending outreach effort on businesses that were never strong web-development prospects in the first place.

The system teaches the buyer to reject businesses when there is no meaningful, current, defensible web-development opportunity.

## Benefit 4 — Have a real reason to start the conversation

The system helps the buyer avoid generic messages such as:

> I noticed your website could use some work.

Instead, outreach is based on:

```text
verified finding
  ↓
business consequence
  ↓
relevant improvement
  ↓
concise outreach angle
```

Translate this benefit into:

> Give the prospect a concrete reason to pay attention instead of sending another generic web-design pitch.

---

# 4. Secondary Strategic Benefit — Own the Process

A fifth benefit can appear later in the page:

> Understand and control your client-acquisition system instead of depending entirely on a black-box lead product.

Do not frame this as an attack on Apollo, Hunter, or other tools.

The point is that the buyer learns how the pieces fit together and can choose which tool performs each job.

# 10. Design / Implementation Constraints

In particular:

- Use Starwind UI as the default primitive library.
- Before creating a common UI primitive, check whether Starwind already provides it.
- Compose project-specific sections from Starwind primitives where appropriate.
- Astro first; Svelte only for genuine client-side state.
- No `<style>` blocks in Astro or Svelte.
- No inline visual `style` attributes.
- No CSS modules or page-specific CSS files.
- Use Tailwind utility classes only in component/page markup.
- Use semantic theme classes and established design tokens.
- Do not introduce arbitrary raw colors in markup.
- Do not introduce routine arbitrary Tailwind values.
- Add reusable visual values to the Tailwind v4 theme in `src/styles/starwind.css` when necessary.
- Preserve accessibility and responsive behavior.
- Do not replace existing working components solely for stylistic novelty.

This is primarily a **messaging hierarchy and content revision**, not a request for a new visual system.

Reuse the existing visual language where it supports the revised message.
